Technical Assignment · Senior Backend & Platform Engineer

AI-Enabled Clinical Intelligence Platform

Architecture, retrieval design, evidence provenance, and a plan for taking ownership of a platform someone else built.

Rutik Pol Submitted to Centrix Ten sections, one per prompt

Where the scale actually is

20,000 queries/day is 0.23 QPS average. Serving is not the hard part. Ten million documents is roughly 300 million chunks, and an embedding-model upgrade is a multi-day rebuild. The index is the scale problem; the API is not.

Where agents do not belong

A bounded planner over a fixed sub-query taxonomy on the clinical path; free-form agent loops offline only. You cannot regression-test a loop that takes a different path each run, and the same question must return the same answer.

What a citation is

A foreign key, not a regeneration. Every generated statement stores the passage IDs it was produced from, and every passage resolves to a document version, section, page and character span. Nothing is re-derived to cite it.

SECTION 01

End-to-End Platform Architecture

Three planes that fail independently. The knowledge plane is batch and interruptible; the query plane is synchronous and always warm; the platform plane is the part that has to hold when a hospital's security team asks.

The organising decision is that ingestion and query share nothing but the index. Ingestion is a restartable batch job that can run on spot capacity and fall a day behind without a physician noticing. Query is a latency-budgeted synchronous path. Coupling them means a parsing backlog degrades answer latency, which is the first architecture mistake I would look for in the inherited system.

Modular monolith for the API, separate worker and ingestion fleetsThree deployables. At 0.23 QPS, service decomposition buys nothing and costs distributed transactions and on-call surface.Discipline. Module boundaries need enforcing in review, since nothing physically stops a cross-import.

SECTION 02

Ingestion & Versioning

Separating the guideline as a concept from the guideline as a published artefact is what makes both the 2027 supersession and the 2026 audit query answerable from the same schema.

Parsing: format-specific, because the failure modes differ

FormatApproachRisk it carries
JATS / NLM XML (PubMed Central)Parse directly. Section structure, references and metadata are already marked up — use them rather than re-deriving.Low. This is the cheapest and most reliable path and should be preferred wherever the same content exists in two formats.
HTML (society and publisher sites)Readability-style main-content extraction, then rebuild the heading tree from h1..h4.Boilerplate leakage and silent template changes. Needs a per-source extraction test.
PDF with a text layerPyMuPDF for text and coordinates, plus a layout model for multi-column and table regions.Reading order in two-column journal layouts. Getting this wrong interleaves two paragraphs into nonsense.
Scanned or complex-layout PDFLayout-aware pipeline (Docling or AWS Textract) with OCR confidence retained per block.The expensive path. Route to it only when the text-layer heuristic fails.
The domain-specific one

Tables are a patient-safety surface, not a parsing nicety. A dosing table is where the actual clinical instruction lives, and a mis-parsed cell can turn an eGFR threshold into a dose. Table extraction gets its own confidence score, and anything below threshold is quarantined for human review rather than indexed. This is the one place I would spend manual review budget on day one.

The version model

Three levels, borrowed from bibliographic practice because it is the same problem: a document is the stable concept ("KDIGO CKD guideline"), a version is one published artefact of it with validity dates and a status, and a section is an addressable region within that version carrying page number and character span. Chunks hang off sections. Every citation resolves through this chain, which is why Section 5 gets to treat citation as a lookup.

Retrieval applies status = 'current' as a default filter, so the 2027 text wins without any ranking heuristic. Superseded content stays indexed and reachable through an explicit as_of parameter — which exists because "what did the guideline say when I treated this patient in March 2026" is a real clinical and medico-legal question, not a nice-to-have.

Deduplication, at two levels

The same guideline routinely arrives three times: publisher PDF, PubMed XML, society HTML. Exact duplicates are caught by a normalised content hash and by identifier (DOI, PMID, ISBN). Near duplicates need MinHash over shingles, with embedding cosine as a secondary signal. On a match the pipeline picks a canonical representation by format preference (XML over HTML over PDF) and keeps the others as alternate manifestations rather than deleting them, because the PDF is what a physician wants to open at the cited page.

Chunking and embedding

  • Structure-aware, not fixed-window. Chunk on section boundaries with a token ceiling. Never split a table or separate a recommendation from its evidence grade — a recommendation retrieved without its grade is worse than not retrieving it.
  • Prepend context to the chunk text. Document title, heading path, publishing body and year go into the embedded text. A chunk reading "reduce dose by 50%" is meaningless in isolation and retrieves against the wrong queries.
  • Version the embedding model on every chunk. embedding_model_id is a column. Re-embedding 300M chunks is a scheduled project, so migration is dual-write into a second index followed by an atomic alias flip, never an in-place update.
SECTION 03

Hybrid Search & Retrieval

Vectors smear exactly the tokens clinical queries depend on. Keyword search is not a legacy fallback here, it is the half that gets drug names and lab thresholds right.

The case for hybrid in this domain is concrete rather than general. Embeddings handle paraphrase well — "kidney impairment" against "renal insufficiency" — and handle precise identifiers badly. SGLT2, NT-proBNP, eGFR <30, ICD-10 E11.22 and a specific drug name are the terms a physician actually types, and they are the terms a dense retriever most reliably blurs into a neighbour. BM25 gets them exactly right. Neither half is sufficient alone.

The pipeline

Metadata filter, then parallel BM25 and vector retrieval at top-50 each, then Reciprocal Rank Fusion, then a cross-encoder rerank down to the 6–8 passages that reach the model. RRF rather than weighted score blending because BM25 scores and cosine similarities live on incomparable scales, and any fixed blend weight is a constant that silently stops being right as the corpus grows. RRF only needs the ranks.

The filter is not optional and it is not a post-processing step: tenant, section status, publication date, specialty, and population (paediatric, adult, pregnancy). A retrieval that returns adult dosing for a paediatric question is a correctness failure, not a relevance one.

OptionArgument forArgument againstPosition

Named trigger, not a hunch

Migrate when recall@20 on the golden set falls below 0.90 under production filters, or when chunk count passes roughly 50 million. Until then, keep retrieval behind a single interface with one implementation, and instrument recall continuously so the decision arrives as a dashboard reading rather than an argument. Writing the interface is cheap now; retrofitting it during a migration is not.

The failure mode worth naming explicitly is filtered ANN. Approximate search with a highly selective filter is where naive designs quietly break: pre-filtering shrinks the candidate graph until the traversal cannot reach relevant neighbours, and post-filtering discards most of the top-k before it is useful. With tenant, status and specialty filters all applied, this is the normal case here rather than the edge case, which is the strongest argument for eventually moving to an engine that treats it as a first-class problem.

SECTION 04

RAG & Agentic Workflow

The example query is a multi-condition interaction question. Its answer exists in no single guideline, which is exactly why it needs decomposition — and exactly why it must not need autonomy.

"How should treatment differ for a patient with heart failure, CKD and type 2 diabetes according to current guidelines?" is not one retrieval. Three separate guideline bodies each address one condition, and the clinically interesting content is where they modify each other: agents indicated across all three, dosing that changes with renal function, monitoring requirements one guideline introduces that another does not mention. Single-shot retrieval returns three disconnected summaries and misses every interaction.

Where an agent earns its place, and where it does not

StageApproachReasoning
Query understandingSingle LLM call, structured outputDeterministic shape, cheap, testable. Extracts conditions, population and intent, normalising to ontology codes so filters can be applied.
DecompositionBounded planner — agentic in spirit, constrained in factThe model chooses which sub-query types apply and how to phrase them, from a fixed taxonomy with a hard cap. Genuine flexibility where it helps, with a bounded and enumerable output space.
Retrieval qualityOne corrective retryIf every reranker score sits below threshold, the query is rewritten once and retried. This catches real vocabulary mismatch. Unbounded self-correction catches only slightly more and costs a latency guarantee.
Generation and validationStraight-line, no agencyTwo calls with fixed prompts. Every added hop is another opportunity to lose the passage IDs that make the citation chain work.
Ingestion QA, conflict mining, eval-set generationFull agentic workflows, offlineNo latency budget, no user waiting, and a human reviews the output before it affects anything. This is where autonomy is genuinely worth having.
Where I would deliberately avoid agents

No open-ended agent loop on the clinical answer path. Four reasons, in order of how much they would cost: it is untestable — you cannot build a regression suite against a control flow that differs per run, so quality becomes unmeasurable exactly where measurement matters most; reproducibility is a medico-legal requirement, and the same question asked twice must not produce materially different guidance; latency and cost become unbounded against a p95 SLA; and each additional hop is a chance to drop provenance. If the eval set later shows a class of query the fixed taxonomy cannot decompose, I would extend the taxonomy before I extended the autonomy.

SECTION 05

Provenance, Citations & Reliability

Every control here is a gate that can refuse. The system's most valuable behaviour is declining to answer, and that has to be designed in rather than tuned in later.

The chain is stored, not reconstructed. When the model emits a statement it emits the passage IDs that statement came from, drawn from the closed set that was put in its context. Those IDs are foreign keys. Rendering a citation is a join, so a citation cannot disagree with the evidence, and an ID the model invents fails validation immediately because it does not exist.

Defence in depth, cheapest gate first

GateCatchesCost
1. Retrieval thresholdIrrelevant retrieval. If the best reranked passage is below threshold, generation never runs.Free. One comparison.
2. Closed-set ID validationFabricated citations. Any passage ID not in the context is a hard failure, not a warning.Free. A set membership test.
3. Freshness assertionOutdated evidence. Every cited section must still be effective, or the answer carries an explicit staleness notice.Free. Already in the join.
4. Entailment checkUnsupported claims. Each statement is checked against its own cited passages by an NLI model or a small judge model.One small-model call per statement. The only gate with real cost, and the one that catches the plausible-sounding fabrication.
5. Physician feedbackEverything the first four miss. A flagged answer becomes an eval-set case.Product surface plus review time. The only gate that improves the others.

When evidence is insufficient

The system abstains, and abstention is a designed output rather than an error path. It returns the closest evidence it did find and states plainly that no current guideline directly addresses the combination asked about. Abstention rate is a tracked metric, and a rising rate on a particular topic is the clearest signal available that the corpus has a gap — it routes to the content team, not to the on-call engineer.

When evidence conflicts

Do not resolve it. Surface it. Two guideline bodies disagreeing is a real and common state of medical evidence, not a data quality defect to be smoothed over. The system presents both positions attributed by issuing body, publication date and evidence grade, and names the axis of disagreement. Physicians are trained to weigh conflicting evidence; the platform's job is to put both in front of them with provenance intact. Silently picking a winner is the worst available behaviour precisely because it is invisible — the physician cannot tell that a choice was made on their behalf.

SECTION 06

Core Backend & Multi-Tenancy

Row-level security handles the relational data. The vector index is the part it does not cover, and that is where tenant isolation actually gets decided.

Services and data

Three deployables: a FastAPI application (query, corpus admin, tenant admin), a worker fleet (Celery or ARQ over Redis and SQS), and the ingestion pipeline orchestrated by Airflow. The core schema is tenant, user, membership, role, the corpus chain from Section 2, then query, answer, statement, citation, feedback, audit_event and ingestion_job.

Tenancy: three tiers, chosen per data class

Data classModelWhy
Tenant operational data
users, queries, answers, audit		Shared schema, Postgres row-level securityIsolation is enforced by the database, so an ORM mistake or a forgotten WHERE cannot leak across tenants. Application-level scoping is one missing clause away from an incident.
Public medical literatureSingle shared corpusThe KDIGO guideline is identical for every customer. Duplicating 300M chunks per tenant is indefensible on cost, and it multiplies every re-embedding job by the customer count.
Tenant-private content
hospital protocols, formularies		Physically separate index or collectionNot a filter column. For the data whose leakage would end the company, physical separation is worth more than a predicate that one code path can forget to apply.
Two failure modes worth pre-empting

RLS does not protect the vector index. An ANN search is not a row scan, and a retrieval path that forgets its tenant filter returns another hospital's protocol with no database-level objection. The mitigation is that no caller constructs a search directly — one retrieval function applies the tenant predicate, and there is a test asserting that a cross-tenant query returns zero rows.

PgBouncer in transaction mode breaks session-scoped RLS. Setting app.tenant_id once per connection silently leaks across pooled sessions. It has to be set per transaction, via SET LOCAL inside the request's transaction scope. This is exactly the class of subtle inherited defect I would grep for in week one.

Access, audit and the enterprise surface

  • OIDC and SAML per tenant. Hospitals arrive with Entra ID or Okta and will not create separate accounts. SCIM for provisioning and, more importantly, deprovisioning — a clinician who leaves must lose access the same day.
  • Roles: physician (query, view own history), librarian (curate tenant corpus), tenant admin (users and access), auditor (read-only across the tenant, no clinical content authoring). Permissions are checked at the service boundary, never in the UI.
  • Append-only audit log in its own table with no update or delete grant. Every query, every answer, every citation, every corpus change, every access grant. Retention per contract. This is a compliance requirement and it is also the debugging tool that makes an answer from six weeks ago explainable.
  • Redis carries sessions, rate limits, idempotency keys, the query-embedding cache and reranker results. Not final answers — Section 8 covers why.
SECTION 07

Scale, Cloud & Observability

The stated numbers describe a small serving problem attached to a large indexing problem. Sizing the API for the query volume and the pipeline for the corpus is the whole answer.

What the numbers actually say

StatedDerivedConsequence
20,000 queries/day0.23 QPS mean, roughly 2–4 QPS at a clinic-hours peakThree warm API pods are sufficient. Serving capacity is not a design constraint and should not be treated as one.
100,000 registered physiciansPerhaps 5,000 weekly active, low concurrencyA user-table problem, not a load problem.
10 million documents~300 million chunks at ~30 per document; ~1.2 TB of fp32 vectors, ~300 GB at int8This is the scale problem. It sets the index engine, the memory budget and the quantization strategy.
Multiple ingestion pipelinesFull re-embed at 2,000 chunks/s is ~42 hoursAn embedding-model upgrade is a planned project with a dual-write migration, not a background task.

Bottlenecks, in the order they will bite

  1. PDF parsing throughput and cost. The slowest, most failure-prone and most expensive stage, and the one that determines how fast the corpus can grow.
  2. Filtered-ANN recall at 300M vectors. Degrades gradually and invisibly. Only a golden set catches it.
  3. LLM time-to-first-token. Dominates p95 perceived latency once retrieval is tuned.
  4. Cross-encoder reranking. 50 passages is 200–600 ms on CPU. Fine at 4 QPS, and worth the latency for the precision it buys.
  5. Postgres connections. Async workers plus an async API exhaust the pool long before they exhaust the CPU. PgBouncer from the start.

Cloud shape

EKS for the API and workers, because Docker is already the deployment unit and the pipeline stages are long-running in a way Lambda's execution ceiling and cold starts actively fight. Serverless is right for the event glue — S3 notification to SQS to job enqueue — and wrong for the pipeline itself. Karpenter for node autoscaling, KEDA to scale workers on queue depth rather than CPU, which is the metric that actually correlates with ingestion backlog. Ingestion runs on spot: it is idempotent, checkpointed and restartable, which makes it close to the ideal spot workload. RDS Postgres Multi-AZ, ElastiCache, S3 with versioning and Object Lock. Terraform for everything, with the click-ops inventory from the takeover audit imported deliberately rather than left as drift.

Observability that is specific to this system

Generic infrastructure metrics will not tell you the product is broken. One OpenTelemetry trace spans query through retrieval, rerank, generation and validation, with retrieval scores, filter predicates, token counts and model IDs as span attributes. That trace is what makes "why was this answer wrong six weeks ago" an answerable question rather than a shrug. On top of the usual RED metrics and Sentry, the dashboards that matter are: recall@k against the golden set, abstention rate by topic, entailment pass rate, citation-click-through, p95 TTFT, and cost per query.

Disaster recovery, and one asymmetry

Postgres recovers by point-in-time restore in minutes. The index does not — rebuilding it from S3 is measured in days, because the expensive work is parsing and embedding rather than storage. So the RPO and RTO differ by data class: minutes for operational data, and for the index either an accepted multi-day RTO or a warm cross-region replica, depending on what the enterprise contracts actually commit to. Backups are only real once a restore has been performed end to end, which is a day-60 exercise in Section 9 rather than a checkbox.

SECTION 08

AI Cost & Performance

At this volume, engineering time costs more than tokens. That makes the optimisations worth doing early precisely the ones that also improve the answer.

The baseline, so the decisions have a denominator

StageModel classTokensApprox. cost/query
Query understanding + planningSmall~600 in / 150 out< $0.001
RerankingLocal cross-encoder—Compute only
GenerationFrontier~8,000 in / 800 out~$0.036
Entailment validationSmall~2,000 in / 200 out~$0.002
Total, 20,000 queries/day~$780/day, ~$23k/month

Generation is roughly 90% of the bill, and its input context is roughly two thirds of that. Every meaningful optimisation follows from those two facts.

Implement early

  1. Context tightening. Reranking hard to 6–8 passages rather than passing 20 halves input cost and cuts TTFT — and it improves answer quality, because a model given twenty passages attends worse than one given eight. The strongest optimisations here are the ones that are not trade-offs at all.
  2. Model routing by stage. Understanding, planning and validation do not need a frontier model. That is most calls by count and a small fraction of spend once routed.
  3. Cache the retrieval layer, not the answer. Query-to-embedding is an exact-match cache with a high hit rate on common questions. Reranker results likewise. Both are safe.
  4. Stream the response. Perceived latency is TTFT, not total. Streaming tokens and rendering citations progressively is a large UX win for a small amount of work.
  5. Move non-interactive work off the request path. Batch literature reviews and periodic digests are queued jobs with a notification, not held HTTP connections.
One optimisation I would refuse

No semantic caching of final answers. Two clinically distinct questions can sit close enough in embedding space to be treated as a cache hit — a paediatric and an adult dosing question, or the same question with and without a contraindication. Serving one answer for the other is a patient-safety failure disguised as a latency improvement. Exact-match caching on a normalised query, scoped to the corpus version and invalidated when it changes, is the safe form and is where I would stop.

Defer until scale justifies it

DeferredWhy not yetWhat triggers it
Self-hosting the generation modelA multi-GPU node plus the operational burden costs more than $23k/month of API spend, and adds a serving system to run.Spend reaching roughly 3–5× the equivalent infrastructure cost — or, more likely first, an air-gapped or data-residency contract. That is a compliance trigger, not an economic one.
Fine-tuning a domain embedding modelReal gains available on biomedical text, but they are unmeasurable without an eval set and unguided without query logs.A golden set exists and retrieval recall is the demonstrated bottleneck.
Cascade routing, prompt compressionMeaningful complexity, and the savings are speculative without production traces.Generation spend becoming a material line item rather than a rounding error.

The highest-leverage artefact of month one

The golden eval set, built with clinicians. It converts every subsequent change from "seems better" to "measurably better," and it is the only defence against a refactor quietly degrading answer quality. A RAG system fails silently — nothing gets paged, answers simply get worse — so without measurement, taking ownership means taking responsibility for something whose quality nobody can observe.

Five areas audited first

  1. Tenant isolation and PHI handling One cross-tenant leak is existential. Is the vector search actually filtered by tenant, or only the SQL? Is RLS enabled and does connection pooling defeat it? Does any log, trace or prompt contain PHI? Is every third-party processor covered by a BAA?
  2. Secrets, IAM and public exposure Credentials committed to the repository, over-broad IAM roles, publicly reachable buckets or database endpoints, no rotation. Cheapest category to check and the worst to discover from outside.
  3. Data durability and the rebuild path Are raw source documents retained immutably? Can the index be rebuilt from them, and has anyone tried? If the vector store is the only surviving copy of the parsed corpus, that is a company-ending single point of failure that no backup schedule addresses.
  4. Retrieval and answer quality — the silent risk Most likely there is no eval set and no measurement, so quality is unknown rather than good. I would read the actual retrieved passages for fifty real queries. This is the risk least likely to be on the partner's own list.
  5. Deploy, rollback and migrations Can we deploy without the partner? Is there a rollback path? Are schema migrations reversible and tested? If deployment runs through a person at another company, ownership has not transferred regardless of what the contract says.

Three decisions with no single correct answer

1. pgvector, or a dedicated vector engine

pgvector: one datastore, transactional consistency between metadata and vectors, RLS for free, no new operational surface. Degrades on filtered-ANN recall and index memory somewhere past tens of millions of chunks. OpenSearch or Qdrant: purpose-built filtered ANN, quantization built in, comfortable at 300M+ vectors — at the cost of a second source of truth and the synchronisation machinery that implies.

Position nowStay on pgvector, which is almost certainly what already exists, and put retrieval behind a single interface with recall instrumented from day one. Ten million documents is the eventual state, not the current one. The migration should be triggered by a dashboard reading — recall@20 below 0.90 under production filters, or 50M chunks — not by anticipation.
2. Agentic, or deterministic, for multi-condition queries

Agentic: handles query shapes nobody anticipated, self-corrects, better on the long tail. Deterministic with a bounded planner: reproducible, testable, bounded in latency and cost, and auditable after the fact.

Position nowDeterministic, with one bounded retry. In a clinical product, reproducibility is worth more than tail coverage, and an untestable path is one whose quality cannot be defended. If the eval set shows a query class the taxonomy cannot decompose, I would extend the taxonomy before extending the autonomy. This is the decision I hold most loosely — evidence from real physician queries could reasonably move it.
3. Shared corpus, or per-tenant isolation

Shared: a fraction of the storage and embedding cost, one re-embedding job, one quality bar to maintain — but every isolation bug is a cross-tenant bug. Per-tenant: trivially auditable, easy to sell into a hospital security review, and a genuine compliance shortcut — at hundreds of times the index cost and a fleet operation for every model upgrade.
